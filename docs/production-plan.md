# Production plan: accounts, passwords, backups, restart, observability

Status 2026-09-23: §1 accounts, §2 PBKDF2 and the timed save (§3) are implemented and tested; backups,
restart supervision, observability and Terraform wait for deployment. Gameplay work (Rookgaard PvP etc.) continues in the meantime.

## Facts this plan is built on

- The local database (not deployed yet) was created from `server/sql/seed.sql`. It has the God account **9 / 9**, test accounts 1-6 with
  passwords "1"-"6", 111111 / tibia and 222222 / test. seed.sql is in git, so every password in it is public.
- `PasswordType = "plain"`: passwords are stored as typed. The engine also supports `md5` and `sha1`, both
  **unsalted** (`tools.cpp passwordTest`).
- **The 7.4 protocol has no encryption** (RSA/XTEA arrived in 7.7): account number and password travel in clear
  text on every login. Hashing protects the database, not the wire. Players must be told not to reuse passwords.
- **Nothing saves on a timer.** Players are saved on logout; houses/map on `/save` or a clean shutdown
  (`Game::saveServer` is only called from commands and `doSaveServer`, and no global event calls it). A killed
  process loses everything since each player logged in. Auto-restart without periodic saves still loses progress.
- The server is a Windows build (MSVC + vcpkg, `timeBeginPeriod`, `build.bat`). It uses ~2.5 GB RAM with the full map.
- There is no Terraform or infra code in this repo yet.

| C | Rookgaard premium | yes | Premium Tester, Oracle Tester |
| D | Rookgaard free | no | Free Tester, Rook Tester |

- Account numbers: random 7 digits (like 5470767), generated once, never sequential, never in git.
- Passwords: 20+ random characters, generated by the provisioning script, never in git or chat.
- The old accounts (1-6, 9, 111111, 222222) are deleted on production; their characters move to A-D.
- Account "Mintwall" (111111): delete on production (it was the first smoke-test character).

How:
- `seed.sql` stays **dev/test only** (the test suite and local play keep 3/3 etc.). Production never loads its accounts.
- New `tools/provision-accounts.py`: creates/moves A-D in a given database, reads each account's number and

  configured `PasswordType`; prints nothing secret. Idempotent (safe to run twice).
- Not deployed yet, so no emergency change is needed; production is provisioned by the script from day one.
- Test: a pytest that provisions a scratch DB with fake secrets and checks the accounts, premium, characters and
  that no seed account is left; plus a check that seed.sql is never loaded by the production path.

## 2. Password storage

Option 1, `sha1` (engine-supported today): a config switch plus hashing the existing passwords once. Unsalted
SHA-1 falls quickly to precomputed tables if the database leaks.

Option 2 (recommended): a small engine change to `passwordTest` to store `pbkdf2$iterations$salt$hash`, using a
vetted implementation (for example OpenSSL's `PKCS5_PBKDF2_HMAC`, already available through vcpkg), and still
accept the legacy forms during migration. The provisioning script and the future account-creation page write the same format.

Chosen: option 2. Design:
- Format `pbkdf2_sha256$600000$<salt b64>$<hash b64>` (16-byte random salt, OWASP 2023: 600,000 iterations of
  HMAC-SHA256). Engine: OpenSSL `PKCS5_PBKDF2_HMAC` (add `openssl` to vcpkg.json; also builds on Linux later).
  Scripts: Python `hashlib.pbkdf2_hmac` (standard library), same format.
- **Not on the network thread.** Logins are checked in `onRecvFirstMessage` on the single asio thread that serves every
  connection (connection.cpp:264; ProtocolLogin:142, ProtocolGame:497). 600,000 iterations cost a few hundred
  ms of CPU; there it would stall everyone's packets, and login spam would lag the server. The check goes to a
  small worker pool (2 threads, bounded queue; a full queue answers "try again") and the result is posted back.
- **Throttle failures per IP** (e.g. 5 failed logins per minute, then refuse for a few minutes) so the
  expensive hash cannot be used to exhaust the CPU.
- Legacy plain/sha1 rows still log in during migration and are rehashed on the next successful login.

Either way:
- Migration: hash every existing password in place (script, run once, backup first).
- Tests: login works with the hashed password, fails with a wrong one, and no plain password remains in the DB.

## 3. Backups and restart

### Saves (prerequisite)
- Global event `doSaveServer` every 10 minutes (players + houses/map), plus a save on clean shutdown (already the case).
- Test: change a character, wait for the save, read the DB without the player logging out.
- Done 2026-09-23, and the save no longer freezes the game: it is captured as SQL on the game thread and
  written by a background writer (own SQLite connection, WAL, one transaction per save). 100 players online:
  ~34 ms on the game thread (was ~570 ms), ~65 ms of writing off-thread. Logout saves use the same writer;
  a login waits for that player's pending write; shutdown waits for the writer. Crash loss = at most one
  SaveInterval of progress.

### Backups
- **Online SQLite snapshot every hour**: `sqlite3 db.db3 ".backup ..."` (or `VACUUM INTO`), which is consistent while
  the server writes. Compress, upload to S3 with `aws s3 cp`.
- S3 bucket: versioning on, SSE-KMS encryption, public access blocked, lifecycle hourly→30 days, daily→1 year (or
  Glacier after 90 days), Object Lock optional against deletion.
- **EBS snapshots daily** via AWS Backup (whole data volume: DB, map saves, logs), 14-day retention.
- Targets: RPO 1 hour (hourly snapshot; periodic save makes it ≤ 10 min of play); RTO 30 minutes.
- **Restore drill**: a scripted restore into a scratch instance/DB, run monthly and once before launch. Backups
  that were never restored count as missing.
- Alarm when the newest backup in S3 is older than 2 hours.

### Restart
`forever` is a Node.js process manager; for a native server, the OS supervisor does the same job better:
- **Linux**: a systemd unit with `Restart=always`, `RestartSec=5`, and `StartLimitBurst` so a crash loop stops and alerts.
- **Windows**: run it as a service (NSSM or `sc.exe` with failure actions "restart after 5 s").
- Graceful stop: the service stop sends the server a clean shutdown (save first), not a kill.
- Every restart is logged and counted (metric `ServerRestarts`).

**Decision needed: Linux or Windows on AWS.** Linux (Amazon Linux 2023 / Ubuntu) is cheaper, systemd and the
CloudWatch agent are simpler, but the build needs porting (Avesta builds on gcc; our Windows-only bits such as
`timeBeginPeriod` need `#ifdef`s, and the test suite then runs on Linux too). Windows keeps today's build unchanged but
costs more (license: roughly +$20/month at 2 vCPU) and makes automation heavier.

## 4. Observability and alerts

- CloudWatch agent on the instance:
  - `procstat` for the server process (up / memory / CPU)
  - memory and disk
  - ships `server.log` to CloudWatch Logs
- Log metric filters: `Lua Script Error`, crashes / abnormal exits, "Server saved" (save age), login errors.
- **External health check**: a Lambda (or CloudWatch Synthetics) every minute asks the server's status protocol on port
  7171 (the "info" request `status.cpp` answers) → metrics `ServerUp` and `PlayersOnline`. This catches "process up
  but not answering", which procstat cannot.
- Alarms → SNS → Slack (AWS Chatbot, or a small Lambda posting to a webhook stored in SSM):
  - server not answering for 2 minutes
  - more than 3 restarts in 15 minutes
  - newest backup older than 2 h, or no save in 20 min
  - disk above 80 %, memory above 85 %
  - burst of Lua errors
- Dashboard: players online, restarts, save/backup age, CPU/memory, Lua errors.

## Terraform (review before launch)

The Terraform isn't in this repo. Either add it here (`infra/`) or point me at its repo. Checklist it must meet:
- **State:** remote state in S3 with DynamoDB locking, versioned, encrypted.
- **Networking:**
  - VPC and a security group opening only 7171/7172 TCP to the world
  - no SSH from the internet: use SSM Session Manager
- **Instance and IP:**
  - EC2 with an Elastic IP; the client is patched with this IP, so it must never change
  - IAM role: SSM, CloudWatch agent, write to the backup bucket, read the specific SSM parameters
  - separate gp3 data volume, `DeleteOnTermination = false`
- **Backup and alerting resources:** S3 backup bucket and AWS Backup plan as in §3; alarms, SNS, and the Chatbot/Slack integration as in §4.
- **Secrets:** SSM SecureString for account passwords and the Slack webhook; nothing in `.tfvars` or git.
- **CI:**
  - `terraform fmt -check`, `validate`, `tflint`, `checkov`/`tfsec`
  - `plan` on PR, manual `apply`
- **Deploy:** a versioned build artifact (server + data) uploaded to S3 and pulled by the instance, with rollback to the previous version.

## Passwords on the wire (7.4 has no encryption)

The 7.4 client sends account number and password in clear text. Two layers:
- Tell players: MOTD / login message / website: "use a password you use nowhere else".
- Encrypt it anyway: every player runs our `mintwall.dll` inside the client. The DLL can wrap the client's
  socket in TLS (hook `connect`/`send`/`recv`, Windows SChannel); in front of the server, stunnel locally or an
  AWS NLB TLS listener terminates it and forwards plain TCP to 7171/7172. The game protocol and server stay as
  they are. A client without the DLL would no longer connect (acceptable: the IP patch already makes our client
  a separate build).
